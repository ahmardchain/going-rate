Going Rate

An agent should know the price of a job before it asks you to pay. Before you tap your passkey on a Kite spending session, Going Rate shows what people usually approve for that kind of task, so the agent asks for the right caps the first time and the run doesn't stop halfway for a second approval.

How it works

1. Agent drafts an askA task summary plus the caps for kpass session create: per payment, total, duration.
2. SERV classifies itThe OpenServ inference API, with a fixed system prompt compiled once into a cached flowchart, puts the summary into one of 8 task types.
3. Code computes the rateMedians and percentiles of past approvals for that type, compared with the ask: in line, high or low, plus suggested caps. SERV then explains the card in one sentence, using only numbers code gave it.
4. You approve onceThe going rate goes into Kite's --task-summary, so it's on Kite's own approval screen. After your decision, kpass session status records the outcome.
  • What's real here: two live SERV Reasoning calls per card (gpt-6-luna: classify, then explain), the rate math, the Kite-verified session decisions, and every payment on the ledger.
  • What's simulated on this page: the passkey. The going-rate CLI makes the real kpass session create call, waits on kpass session status, pays with kpass session execute, and records Kite's actual result. The contrast demo shows one such run.
  • What's seeded: the starting pool (93 rows, labelled seeded: true). kpass activity only covers one account, so a shared pool of real approvals doesn't exist yet. Going Rate starts one.
