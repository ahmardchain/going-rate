How it works

1. Agent drafts an askA task summary plus the caps for kpass session create: per payment, total, duration.
2. SERV classifies itA fixed system prompt, compiled once by SERV into a cached flowchart, puts the summary into one of 8 task types. SERV never handles amounts.
3. Code computes the rateMedians and percentiles of past approvals for that type, compared with the ask: in line, high or low, plus suggested caps.
4. You approve onceThe card shows before the passkey. After your decision, kpass session status records the outcome and the rate updates.
  • What's real here: live SERV Reasoning classification (gpt-6-luna), the rate math, and outcome recording.
  • What's simulated on this page: the passkey. The going-rate ask CLI makes the real kpass session create call, waits on kpass session status, and records Kite's actual decision.
  • What's seeded: the starting pool (93 rows, labelled seeded: true). kpass activity is per account, so a shared pool of real approvals doesn't exist yet. Going Rate starts collecting one.
